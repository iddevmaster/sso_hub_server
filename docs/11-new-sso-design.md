# 11 · การออกแบบ SSO ใหม่แบบหลายโรงเรียน (ร่าง)

สถานะ: **ร่างเพื่อตกลงร่วมกัน** ระบบใหม่จะเป็น repo ใหม่ (Laravel + Passport) เมื่อสร้าง repo แล้วให้ย้ายเอกสาร 09–11 ไปไว้ที่นั่น
ระบบเดิม (repo นี้) จะถูกเก็บไว้ดูข้อมูลเก่าเท่านั้น

## เป้าหมาย

1. รองรับทุกโรงเรียนใน DTMS โดยข้อมูลแต่ละโรงเรียนแยกกัน
2. DTMS เป็นแหล่งข้อมูลจริงของนักเรียน คอร์ส และสาขา SSO เก็บเท่าที่ต้องใช้ login และตอบระบบปลายทาง
3. ระบบปลายทางเดิมใช้งานต่อได้โดยแก้น้อยที่สุด: SmartHub, KST-Plus, Check-Before Driving
4. โรงเรียนอื่นนอกจาก IDDrives เข้าใช้ระบบปลายทางได้ **แต่แก้ไขข้อมูลไม่ได้**

## ขอบเขต

| SSO ใหม่ทำ | SSO ใหม่ไม่ทำ (ย้ายไป DTMS หรือเลิก) |
|---|---|
| หน้า login, เลือกโรงเรียน, consent ของ OAuth | สร้าง/แก้นักเรียน คอร์ส สาขา หน่วยงาน |
| OAuth server (Passport) และ endpoint ข้อมูลผู้ใช้ | import Excel, ถังขยะนักเรียน |
| รับข้อมูลจาก DTMS ([09](09-dtms-sync-design.md), [10](10-dtms-sync-contract.md)) | ดึงจาก EM / POS (`fetch:*`) |
| กำหนดว่าระบบปลายทางใดเปิดให้โรงเรียนใด ในระดับใด | ระบบสิทธิ์ละเอียดแบบ Spatie สำหรับนักเรียน |
| แอดมิน: client, สิทธิ์ต่อโรงเรียน, รีเซ็ตรหัสผ่าน, สถานะการซิงก์ | |

## โมเดลตัวตน

- **บัญชี = (โรงเรียน, เลขบัตร)** ตรงกับ DTMS (`students` unique `(school_id, id_number)`) คนเดียวกันเรียนสองโรงเรียนจะมีสองบัญชี สองรหัสผ่าน ข้อมูลไม่ปนกัน
- ทุกบัญชีมี **`sub` (UUID)** ที่ไม่เปลี่ยนตลอดอายุ ใช้เป็นตัวระบุหลักให้ระบบปลายทาง แทนเลขบัตร
- **แอดมินของ SSO** อยู่คนละตาราง (`admins`) ไม่ปนกับนักเรียน
- รหัสผ่านเริ่มต้นของบัญชีใหม่ใช้กติกาเดิม (เลขบัตร) ไปก่อน และเพิ่มธง `must_change_password` ไว้สำหรับนโยบายบังคับเปลี่ยนในอนาคต
- บัญชีมี 2 ชนิด (`kind`): `student` (มาจาก `students` ของ DTMS) และ `staff` (มาจาก `users` ของ DTMS: เจ้าหน้าที่, ครูฝึก, ผู้ดูแลโรงเรียน)

### สิทธิ์เข้าใช้ของนักเรียน (ตกลงแล้ว)

- นักเรียน login ได้เมื่อมีการลงทะเบียนอย่างน้อยหนึ่งรายการที่สถานะ `active` หรือ `pending_cancellation`
- **สิทธิ์หมดเมื่อเรียนจบ (`completed`) หรือยกเลิก (`cancelled`)** ทุกรายการ บัญชียังอยู่ (ไม่ลบ) ถ้าลงทะเบียนใหม่ภายหลังก็กลับมาใช้ได้ด้วยรหัสผ่านเดิม
- เมื่อการซิงก์พบว่าสิทธิ์หมด SSO ต้อง **เพิกถอน access และ refresh token ของบัญชีนั้นทันที** ไม่เช่นนั้นนักเรียนยังใช้ระบบปลายทางต่อได้นานสุด 30 วันผ่าน refresh token
- Online Course ของ DTMS ใช้ออกใบเสร็จเท่านั้น (เรียน onsite ที่โรงเรียน) จึงไม่มีกติกาพิเศษ การลงทะเบียนชนิดนี้เป็น `completed` ตั้งแต่ซื้อ จึงไม่ให้สิทธิ์และไม่มีผลต่อค่าปัจจุบันของบัญชีโดยอัตโนมัติ

### บัญชีเจ้าหน้าที่และครูฝึก (รองรับไว้ เปิดใช้ทีหลัง)

ตอบว่า "อาจจะ" จึงออกแบบให้รองรับโดยไม่ต้องรื้อ แต่ไม่ต้องทำในรอบแรก:

- **ไม่เก็บรหัสผ่านเจ้าหน้าที่ใน SSO** ให้ DTMS ตรวจเอง: หน้า login ของ SSO มีแท็บ "เจ้าหน้าที่ / ครูฝึก" ใช้ username และรหัสผ่านของ DTMS แล้ว SSO เรียก endpoint ตรวจรหัสผ่านของ DTMS ([10](10-dtms-sync-contract.md)) เจ้าหน้าที่จึงมีรหัสผ่านชุดเดียว และการล็อกบัญชี/ปิดบัญชีใน DTMS มีผลทันที
- ครั้งแรกที่ตรวจผ่าน SSO สร้างบัญชี `kind = staff` ผูกกับ `dtms_user_id` เพื่อให้มี `sub` คงที่
- `/api/user` ส่ง `role: "staff"` (คงค่าเดิมให้ระบบปลายทาง) และเพิ่ม `dtms_role` (`school_admin`, `staff`, `instructor` …)
- `super_admin` ของ DTMS ไม่มีโรงเรียน ไม่ให้ login ผ่านช่องนี้
- ทางเลือกที่สะอาดกว่าในระยะยาวคือให้ DTMS เป็น identity provider ให้ SSO (ปุ่ม "เข้าด้วยบัญชี DTMS") แต่ต้องทำ OAuth server ใน DTMS จึงไม่เลือกตอนนี้

### การ login เมื่อมีหลายโรงเรียน

ระบบปลายทางไม่ต้องส่งข้อมูลโรงเรียนมา:

1. ผู้ใช้กรอกเลขบัตร + รหัสผ่าน
2. SSO ตรวจรหัสผ่านกับทุกบัญชีที่มีเลขบัตรนั้น
3. ตรงบัญชีเดียว (กรณีส่วนใหญ่) → เข้าเลย · ตรงหลายบัญชี → ให้เลือกโรงเรียน · ไม่ตรงเลย → ข้อความผิดพลาดแบบเดียวกับตอนนี้
4. ตรวจว่าบัญชียังมีสิทธิ์เข้าใช้ (มีการลงทะเบียนที่ยังเรียนอยู่) และโรงเรียนของบัญชีได้รับอนุญาตให้ใช้ client นี้ (ดูหัวข้อถัดไป) ถ้าไม่ → ปฏิเสธพร้อมข้อความที่บอกเหตุผล
5. ถ้าระบบปลายทางส่ง `school=<slug>` มาใน URL authorize ให้ข้ามขั้นเลือกได้ (ทางเลือก ไม่บังคับ)

## สิทธิ์ของระบบปลายทางต่อโรงเรียน

ตาราง `client_school_access (client_id, school_id, access_level)`:

| `access_level` | ความหมาย | ตัวอย่าง |
|---|---|---|
| `full` | ใช้งานและแก้ไขข้อมูลได้ | IDDrives กับทุกระบบ |
| `read_only` | เข้าใช้ได้ แต่แก้ไขข้อมูลไม่ได้ | โรงเรียนอื่นหลัง DTMS เสร็จ |
| ไม่มีแถว | login ผ่าน client นี้ไม่ได้ | ค่าเริ่มต้นของโรงเรียนใหม่ |

SSO แค่ **บอก** ระดับสิทธิ์ใน response ของ endpoint ข้อมูลผู้ใช้ ส่วนการ **บังคับ** ว่าแก้ไขไม่ได้อยู่ในระบบปลายทางแต่ละตัว (ตกลงแล้ว: ระบบปลายทางจัดการเอง)

## ระบบปลายทางที่มีตารางผู้ใช้ของตัวเอง

ทั้งสามระบบมีตาราง username/password ของตัวเอง สิ่งที่ต้องตกลงกับแต่ละระบบ:

- **จับคู่ผู้ใช้ด้วย `sub`** ไม่ใช่เลขบัตร ครั้งแรกที่ผู้ใช้เดิมเข้าผ่าน SSO ใหม่ ให้หาด้วย `username` เดิมแล้วบันทึก `sub` ลงไป ครั้งต่อไปใช้ `sub` อย่างเดียว ถ้ายังจับด้วยเลขบัตร คนเดียวกันที่อยู่สองโรงเรียนจะถูกรวมเป็นผู้ใช้เดียวในระบบปลายทาง ซึ่งขัดกับการแยกโรงเรียน
- **เก็บโรงเรียนไว้กับผู้ใช้** เพื่อแยกข้อมูลตามโรงเรียน และใช้ `access_level` บังคับการแก้ไข
- **นักเรียนไม่ควร login ด้วยรหัสผ่านในระบบปลายทางโดยตรงอีก** ให้ผ่าน SSO อย่างเดียว ไม่เช่นนั้นจะมีรหัสผ่านสองชุดที่ไม่ตรงกัน (บัญชีผู้ดูแลของระบบปลายทางเองใช้ต่อได้)
- ข้อเสนอสำหรับ KST Hub โดยละเอียดอยู่ใน [12-kst-hub-sso-notes.md](12-kst-hub-sso-notes.md)
- **Check-Before Driving ต้องเปลี่ยนมาใช้ OAuth** ตอนนี้รับเลขบัตร ชื่อ ประเภทรถ และสาขาผ่าน path ของ URL ซึ่งใครก็สร้าง URL ได้ และทำให้เลขบัตรติดอยู่ใน log

## Endpoint ข้อมูลผู้ใช้

`GET /api/user` (scope `view-user`) คงรูปแบบเดิมเพื่อความเข้ากันได้ และเพิ่มฟิลด์ใหม่:

```json
{
  "sub": "0b9f…uuid",
  "name": "นาย สมชาย ใจดี",
  "username": "1234567890123",
  "role": "customer",
  "courses": [{ "course_type": "20240001", "name": "รถยนต์" }],
  "branch": { "name": "โนนทัน", "brn_id": "IDD0003" },
  "agency": { "name": "โรงเรียนสอนขับรถ ...", "agn_id": "IDD0002" },
  "school": { "id": "51f0…uuid", "slug": "iddriver", "name": "..." },
  "access_level": "full",
  "vehicle_type": "car",
  "dtms_role": null
}
```

- `branch.brn_id` / `agency.agn_id` ของ IDDrives ใช้รหัสเดิม (`IDD000x`) ผ่านคอลัมน์ `legacy_code` เพื่อให้ข้อมูลที่ระบบปลายทางบันทึกไว้แล้วยังตรง โรงเรียนใหม่ใช้รหัสจาก DTMS
- `courses[].course_type` ใช้รหัสประเภทคอร์สเดิมผ่านตารางแมป (ดู [09](09-dtms-sync-design.md))
- `vehicle_type` (`car` / `motobike` / `trailer`) แทนการเดาจากชื่อคอร์สภาษาไทยที่หน้าแรกเดิมทำ ใช้กับ Check-Before
- KST Hub (KST-Plus) ใช้ `/api/user` ไม่ได้เรียก `/api/kst-plus` และอ่านแค่ `username`, `name`, `role`, `agency`, `branch`, `courses[0]` ([12](12-kst-hub-sso-notes.md)) จึง **ไม่ต้องทำ `/api/kst-plus`** แต่คงชื่อ scope `kst-plus` ไว้เผื่อ KST Hub ยังขอ scope นี้
- `/api/i-prompt` ไม่ต้องทำ เพราะ I-Prompt ไม่อยู่ในรายการระบบปลายทางแล้ว
- บัญชีเจ้าหน้าที่: `courses` เป็นอาร์เรย์ว่าง, `branch` เป็นสาขาของผู้ใช้ใน DTMS (school_admin ที่ไม่มีสาขาเป็น `null`)

## Logout

- `/api/logmeout` ของระบบเดิมลบ token **ทุก client** ของผู้ใช้ logout จากระบบหนึ่งจึงหลุดจากทุกระบบ
- SSO ใหม่: เพิ่ม `POST /api/logout` ที่เพิกถอนเฉพาะ token ของ client ที่เรียก และล้าง session ของ SSO เอง คง `/api/logmeout` ไว้ให้ระบบปลายทางเดิมใช้จนกว่าจะย้าย

## การย้ายจากระบบเดิม

| ของเดิม | ทำอย่างไร |
|---|---|
| OAuth client (id, secret, redirect URI) | นำเข้า Passport ใหม่ คง id และ secret เดิม ระบบปลายทางแก้แค่โดเมน (หรือไม่ต้องแก้ ถ้าใช้โดเมนเดิม) |
| access/refresh token | ไม่ย้าย ผู้ใช้ login ใหม่ครั้งเดียว (access token อายุแค่ 1 วันอยู่แล้ว) |
| นักเรียน | ไม่ย้าย ได้จาก DTMS ผ่านการซิงก์ |
| hash รหัสผ่านของนักเรียนที่เคยเปลี่ยนเอง | ทางเลือก: นำเข้าเฉพาะคนที่จับคู่กับบัญชีใหม่ได้ด้วยเลขบัตร (hash แบบ bcrypt ใช้ข้าม Laravel app ได้) |
| แอดมิน/เจ้าหน้าที่ | สร้างใหม่ด้วยมือ (มีไม่กี่คน) |
| ระบบเดิม | หลังย้าย ปิดเว็บ เก็บ dump ฐานข้อมูลไว้เปิดดูเมื่อจำเป็น หรือจำกัดให้เข้าได้เฉพาะแอดมินจาก IP ภายใน |

| 6 | เปิดให้โรงเรียนอื่น: เพิ่มแถว `read_only` ต่อโรงเรียน | โรงเรียนแรกนอก IDDrives ใช้ได้ |
| 7 | (เมื่อต้องการ) login เจ้าหน้าที่/ครูฝึกผ่าน DTMS · ระบบปลายทางสร้างบัญชีเจ้าหน้าที่รายคน | เจ้าหน้าที่สองคนจากสองโรงเรียนได้บัญชีแยกกันในระบบปลายทาง |

ขั้น 1 มาก่อนเพราะเป็นสมมติฐานที่เสี่ยงที่สุด: Passport เวอร์ชันใหม่อาจเก็บ client secret ต่างจาก Passport 11 ที่ระบบเดิมใช้ (เช่น hash secret) ต้องลองนำเข้าจริงก่อนออกแบบส่วนอื่นต่อ

## ตกลงแล้ว

- การบังคับ "แก้ไขข้อมูลไม่ได้" ระบบปลายทางจัดการเอง
- เจ้าหน้าที่/ครูฝึกใน DTMS อาจ login ผ่าน SSO: รองรับไว้ในโมเดล เปิดใช้ในขั้น 7
- สิทธิ์นักเรียนหมดเมื่อเรียนจบหรือยกเลิก
- KST Hub ใช้ `/api/user` ไม่ได้ใช้ `/api/kst-plus`
- Online Course ของ DTMS ไม่เกี่ยวกับ SSO

## เรื่องที่ต้องตัดสินใจ

1. **ช่วงผ่อนผันหลังเรียนจบ** ต้องการให้ดูย้อนหลังได้สักระยะไหม (เช่นดูผลสอบใน Check-Before) หรือหมดทันที
2. **ระบบปลายทางแต่ละตัวพร้อมเปลี่ยนไปจับคู่ด้วย `sub` ไหม** (KST Hub ทำได้ตาม [12](12-kst-hub-sso-notes.md); SmartHub และ Check-Before ยังไม่ได้ดูโค้ด)
3. **นำเข้า hash รหัสผ่านของนักเรียนเดิมหรือไม่**
4. ข้อที่ยังค้างจาก [09](09-dtms-sync-design.md): ตารางแมปสาขาและรหัสประเภทคอร์สเดิม, การแก้เลขบัตรใน DTMS
